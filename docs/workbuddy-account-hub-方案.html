技术方案 · v0.1 草案

WorkBuddy Account Hub
把「切号」从全局状态变更，降级为一次透明的凭据热替换

目标：合并 dsh-workbuddy-connect 与 dsh-workbuddy-switcher， 并补上两者都没覆盖的一层 —— 让正在进行的任务在换账号的过程中不中断、不丢失、可追溯。

基于本机实测数据与插件源码 DSH 0.2.1-rc.2+ 改动量：中 2026-10-21

01先说结论

这三件事值得先摆明，因为它们决定了方案的形状：

  1. 「任务被保持」这件事，其实已经成立了一半。DSH 的会话数据存在 ~/.dsh/sessions/<workspace>/session-*/session.v4.jsonl.zstd，与账号凭据完全无关。换账号不会动这些文件，历史对话本来就在。真正会「断」的不是数据，而是正在跑的这一回合。
  2. 合并有硬技术收益，不只是少装一个包。switcher 的 README 自己写了：两个包如果被装成两份实例，读到的是不同的 process.env，切换就失效。合成单包 = 单进程单解析器 = 切换必然生效，这个坑从根上消失。
  3. 核心增量是一个新东西：会话账本。现有实现里账号是「全局当前选择」，一个进程只有一个。要真正做到「切号不影响别人的任务、断点任务能原地续跑」，账号必须下沉到 会话级 / 请求级解析。这是合并之后才有条件做的升级。

一句话概括产品形态：一个账号池 + 一个会话账本 + 一个按请求解析凭据的调度内核。切号不再是「改一个全局开关」，而是「这个会话下一次请求该用谁的凭据」。

02两个插件现在各自管什么

我把你机器上已安装的两份源码（connect 0.7.8 / switcher 0.2.4）读了一遍，边界很清楚：

四个真实的断点

这些是「切号会掉任务」的实际成因，不是理论问题：

  • 断点 1 · 全局单例。凭据来自一个进程级环境变量，切号等于给所有会话换号。你没法「只把这个任务换到 B 账号，别的继续用 A」。
  • 断点 2 · 生效时机在请求边界。切换只对「下一次」请求生效。一个正在跑的多步任务（工具调用链）如果刚好在旧号额度耗尽时落在中间，整回合失败；即便被 agent/request-error 拦下重试，重试的是那一步，前面的上下文要重发。
  • 断点 3 · 没有回切能力。换号之后，没人记得「这个会话原本是 8bc5fd09 跑的」。想切回去复核、或想知道某段对话花了谁的额度，都查不到。
  • 断点 4 · 实例分裂。双包安装时如果出现两份 connect 实例，切换静默失效 —— 表现为「点了切换没反应」，最难排查的那类问题。

03产品定义与优先级

级别能力验收方式
P0切号不打断正在进行的任务对话进行中触发切换到新账号，当前回合最终正常完成，无报错、无重复工具调用
P0账号池、切换、冷却、签到、跨机同步不退化现有 switcher 的全部用例回归通过
P1每个会话可追溯「用过哪些账号」会话信息面板能看到交接记录（时间、从谁到谁、原因）
P1会话可锁定账号，不参与自动轮换锁定后即使其他账号更优也不切走；仅在该账号 429/402 时解除
P2会话可导出 / 跨机续跑导出包在另一台机器导入后，能继续同一会话

合并只保留一个 LLM 转发入口。所有请求都从 AuthResolver 取凭据，TurnGovernor 所有判定也都在这一处，不存在两套逻辑打架的可能。

05五个关键设计

D1 · 单包单实例

从 connect 的 peerDependency 解耦出来，内部直接调用账号库，不再通过 process.env 做进程间传参。这一步同时消灭断点 4，以及「装了两个 connect 导致切换静默失效」的所有变体。

D2 · 凭据解析下沉到会话级（核心）

现有代码里，模型运行时拿的是一个全局 current() 配置快照。改造后签名变成按会话取：

// 现状：全局单例
createVariantRuntime(config, variant, () => current(), ...)

// 改造：带会话上下文的解析
createVariantRuntime(config, variant, (ctx) => resolveAuth(ctx.sessionId, ctx.region), ...)

解析优先级：会话显式绑定 → 全局当前选择 → 平台默认凭据。这样「切号」的语义从「给整个进程换号」变成「给未绑定的会话换默认号」，已绑定的会话不受影响。

D3 · 回合级交接，而不是会话级重启

额度耗尽时不做「结束当前任务、重开一个」，而是在 agent/request-error 这个 waterfall 里完成交接：判范围 → 选新号 → 标记冷却 → 重试同一步 → 记录一条 handover 事件。关键约束：

  • 交接必须发生在重试同一步的粒度上，工具调用结果不能重放，否则会产生重复副作用（重复写文件、重复下单这类）。
  • 换号后如果目标模型上下文窗口更小，先裁剪再发送，并保证裁剪的是最老的中段而非系统提示与最近工具结果。
  • 交接写进会话事件流，界面上明确显示「本回合第 3 步起由 697af213 接管」，不做成静默行为。

D4 · 会话账本

每个会话一条绑定记录 + 一条交接日志。它解决断点 3，同时是 P2 跨机续跑的数据基础。

D5 · 凭据静态加密

现在 ~/.dsh/workbuddy-accounts/*.json 是明文 accessToken/refreshToken，README 自己也警告过「凭证一旦离开本机无法远程吊销」。合并后账号库会集中承载全部账号，暴露面更大，建议顺手做掉：Windows 走 DPAPI、macOS 走 Keychain、Linux 走 libsecret，失败时降级为口令派生（scrypt）加密。属于额外收益，不阻塞主线。

  "health": { "cooldowns": {}, "checkin": {} }

{
  "version": 1,
  "sessions": {
    "session-092d7be7-…": {
      "accountFile": "697af213-….json",
      "model": "deepseek-v4.1-flash",
      "contextWindow": 200000,
      "pinned": false,
      "handovers": [
        { "at": 1792468402525, "from": "8bc5fd09", "to": "697af213",
          "reason": "hard_credit", "step": 3 }
      ]
    }
  }
}

pinned 是关键开关：置为 true 的会话不参与被动回收，只有真的 429/402 才会被交接走 —— 对应「我想让这个长任务固定用一个账号跑完」。

07切号续跑：完整时序

回合进行中

会话 S 正在跑第 3 步，用的是账号 A 的凭据，此时 A 积分耗尽返回 402。

拦截

TurnGovernor 在最外层 waterfall 拦下错误，读取 failure 里的 provider 与消息体，判定为账号级耗尽。

标冷却

给 A 打上账号级冷却（有重置时间则精确到那一刻，否则按退避策略），落盘。

选号

从健康账号里挑一个：优先已绑定且未冷却、其次上下文窗口满足当前会话、最后按刷新令牌寿命排序。

写账本

在 bindings.json 里追加 handover 事件，更新 accountFile。

重试同一步

返回 {kind:'retry'}，让 agent 重跑第 3 步 —— 之前的工具调用结果原样保留，不重放。

落定

回合正常完成。界面显示交接标记，会话之后继续用 B，除非你手动切回。

这里有个必须承认的边界：如果失败发生在一次工具调用「执行中」而不是「请求边界」，重试无法避免副作用重放。方案的做法是把交接点限制在 LLM 请求边界，并在工具调用前后各记一个 checkpoint；一旦检测到非边界失败，宁可让任务停下并明确告知，也不静默重放。这比假装无损要诚实。

09风险与对策

风险影响对策
明文凭据集中账号库泄露 = 所有账号失效，且无法远程吊销D5 静态加密；导出文件默认带口令；首次运行就提示不要在共享目录存放
签到是逆向的私有接口上游改版即失效，属预期内损耗签到独立降级，失败不阻塞切换与对话；界面上标「暂不可用」而非报错
多账号高频轮换可能触发上游风控，反噬正常使用默认限速：同一模型并发不超过 N；轮换加最小间隔；连续失败回退到"停手"
非边界失败无法无缝续跑个别任务仍可能中断明确失败语义 + checkpoint，不静默重放副作用
DSH 会话格式随版本变化跨机导出包可能失效只通过 DSH 自身 API 读写会话，不直接解 .zstd 二进制；导出包带版本号并做兼容校验
账号共享使用违反服务条款账号被处置定位为「个人自有多个账号的管理工具」，不做账号分发、不做代登录；文档里写清使用边界

最后一条要单独说：这套东西的合理形态是管理你自己名下的多个账号。如果做成对外提供账号池的服务，那性质就完全变了，不在本方案范围内。

10里程碑

阶段交付验证
M0 合并骨架单包、单解析器、能读旧账号库并原样工作卸载旧两包后功能等价，切换立即生效（不再等 30 秒轮询）
M1 会话级解析AuthResolver 带 sessionId、bindings.json 落盘两个会话绑不同账号，互不干扰
M2 交接与可视化TurnGovernor 完整规则、会话面板交接历史、pinned任务跑到一半耗尽额度，自动续跑且界面有标记
M3 加固凭据加密、跨机导出包、限速与风控退避导出导入往返一致；连续轮换不触发限流

建议先做 M0+M1，这两步就能覆盖你最初那句「切号同时保持任务」的主要体感；M2 决定它是不是真的好用，M3 决定能不能长期用。

11需要你确认的四件事

  1. 「保持任务」的范围。是指 DSH 里的会话（本方案主线），还是也要覆盖 WorkBuddy 客户端里的任务列表？后者要动客户端本地数据，风险和工程量都不是一个量级，我建议单独立项。
  2. 要不要跨机器续跑。只同步账号库很简单；连会话一起带走才叫「换台机器接着干」，但会牵扯会话格式兼容。
  3. 账号库加密能否接受一个口令。加密后每次启动要输一次（可记住 N 天），换来的是凭据不再明文躺在磁盘上。
  4. 是改造现有插件，还是起一个全新包。我倾向全新包 workbuddy-hub，把旧的账号库目录做成兼容读取，让你现在这 6 个账号无缝迁过来，而不是在原仓库上打补丁。
方案基于本机实测：~/.dsh 已安装 connect 0.7.8 与 switcher 0.2.4，账号库存有 6 个账号， DSH 会话 19 组 / 单会话记录为 session.v4.jsonl.zstd。文中接口结论均来自对已安装源码的直接阅读。
