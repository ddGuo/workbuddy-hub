两个新需求，一个能直接做，一个要先做决定

「限流时自动无感切换」和「切号后任务全部归集到当前账号」。 前者在客户端场景下有两条完全不同的路，代价差一个数量级； 后者数据层已经验证可行，代码已落地。

01需求变更

编号新需求难度判断
R1任务运行中被限流时，自动无感切换到其他账号有两条路，代价差一个数量级
R2切换账号时，把所有任务同步到当前账号的客户端任务列表数据层已验证可行，已实现

R1 和 R2 有冲突：R2 要求「改数据库归属」，R1 要求「任务不中断」。而改归属必须重启客户端才生效，重启一定中断任务。所以两者要分开处理 —— 归集负责「切完之后能看到全部」，无感切换负责「切的时候不打断」，不能指望同一个动作同时满足。

02R1 · 无感切换能做到什么程度

先明确一件事：客户端的模型请求是客户端自己发出去的 HTTPS 流量，hub 作为外部进程默认看不到、也改不了。所谓「无感切换」，本质是「在请求层换掉凭据并重放，让客户端以为一切正常」。

实测证据（来自客户端 app.asar 与配置）

探测项结果含义
客户端代理支持存在 WORKBUDDY_PROXY_ENV_KEYS / WORKBUDDY_PROXY_SOURCE客户端会读代理配置，可被指向本地代理
自定义证书校验无 setCertificateVerifyProc没有拦截证书校验的钩子，系统信任的根证书会被接受
证书固定（pinning）未发现有效字符串证据MITM 大概率不会被 pinning 挡住
API 端点www.workbuddy.cn（另有 staging）域名集中，代理规则简单
错误码客户端内不含 soft_rate / hard_credit那是 DSH 插件的分类；客户端侧要按 HTTP 状态码判断

两条路

L1 · 检测 + 自动切号 + 提示重试

半自动 · 零侵入 · 本周可交付
  • 监听数据库里任务状态变 error
  • 读会话 jsonl 尾部，识别限流关键词
  • 自动切到健康账号（含归集）
  • 重启后把任务拉回前台，给一个「继续」按钮

损失：一次点击 + 一次重启（约 5 秒）。收益：不需要证书、不碰网络栈、不会被客户端升级打穿。

L2 · 本地代理 + TLS 中间人

真无感 · 重 · 1–2 周
  • 客户端走 127.0.0.1:port 代理
  • hub 自签 CA，安装进系统信任区
  • 解密请求 → 识别 429/402 → 换 token 重放
  • SSE 流式响应原样透传

代价：装根证书（管理员权限、安全责任转移）、流式透传复杂度、客户端升级可能改端点。

我的建议：先做 L1。它解决的是「不用手动找账号」这个真实痛点，代价是可预期的一次重启。L2 能把最后那 5 秒也吃掉，但它把「你的所有 API 流量经过我的中间人」变成默认行为 —— 这个决定应该单独做，而不是顺手塞进来。

如果之后要上 L2，实现时只需要替换「检测到限流之后做什么」这一段：L1 是切号重启，L2 是换 token 重放。上层的判定逻辑（什么算限流、冷却多久、选哪个账号）完全复用。

03R2 · 任务归集

做法很直接：把 sessions.user_id 统一改成当前账号，客户端原生列表就会显示全部任务。关键是确认这个改动安全。

实测前提

检查项结果为什么重要
会话传输方式18 条全部 transport='local'不上云，改归属不会被服务端覆盖或回滚
触发器 / 视图0 个没有级联副作用
外键引用无（session_usage 按 session_id 关联）不会破坏关联完整性
索引涉及 user_id 的 4 个索引都是 WHERE transport='cloud'local 行不在索引里，改写不触发索引维护问题

设计

// 归集时：改归属前先把原始归属记下来
UPDATE sessions SET user_id = :target WHERE user_id <> :target;

// ~/.workbuddy-hub/ownership.json
{
  "unified_to": "db0427fd-…",
  "sessions": { "9bb9bbc1-…": "4dba68a4-…", "95ab5ada-…": "8bc5fd09-…" }
}

四个设计要点：

  • 幂等。只对「归属表里还没有」的会话记录原始 uid。重复执行不会把已经改过的 uid 当成原始值再记一遍 —— 否则回滚会把任务错误地塞回上一个中转账号。
  • 可回滚。hub unify --rollback 按归属表逐条恢复。这是改数据库的前提。
  • 先快照。写库前用 SQLite 在线备份接口做一致性快照（WAL 里未 checkpoint 的数据也会带上），落在 ~/.workbuddy-hub/backups/。
  • 真实归属仍可追溯。hub 自己的界面按归属表显示真实账号，只有客户端原生列表被「抹平」。

还没验证的一件事：客户端启动时会不会按当前 uid 清理「不属于自己」的会话。静态分析看不到这种行为，只能实测。所以第一次真实归集建议在备份完整、且你不在跑任务的时候做，重启后如果列表异常，一条 --rollback 就能恢复。

04归集 + 切号的完整时序

两个动作合并成一个「切换」操作，顺序不能颠倒 —— 先退出再改库，避免与客户端抢写锁。

前置检查

目标账号凭据有效；统计当前有多少 working 任务并明确告知会中断。

双备份

凭据文件 → backups/workbuddy-desktop.*.info；数据库 → backups/workbuddy-*.db（在线快照）。

退出客户端

优雅关闭，轮询 pid 确认退出；超时才强制结束。

写凭据

用 at-rest 密钥封装目标账号令牌，原子写入 auth 文件。

归集任务

补齐原始归属表 → 一个事务改完所有 user_id → 回读校验。

启动客户端

拉起客户端，等 auth 文件被重新写入确认登录成功；任一环节失败自动回滚两份备份。

06需要你定的三件事

  1. L2 要不要做。要装一张自签根证书到系统信任区，之后你机器上所有走代理的 HTTPS 都多一个中间人（只处理 workbuddy 域名，但证书是系统级的）。这是安全决策，不是技术决策，我不替你定。
  2. 归集做成切号的默认行为吗。是的话，每次切号都会改 user_id；不是的话，需要单独一个「同步任务到当前账号」按钮。
  3. 什么时候做真实切号验证。它会重启客户端并中断当前会话。建议你手头没有任务在跑的时候，我把 --force 之后的进程控制补完，你跑一次。
R1 的代理与证书结论来自对 D:\WorkBuddy\resources\app.asar 的字符串检索 （WORKBUDDY_PROXY_ENV_KEYS、setCertificateVerifyProc 计数）； R2 的结论来自 workbuddy.db 的 schema 与索引定义。两者均为只读探测，未修改任何客户端文件。
