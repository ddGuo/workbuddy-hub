workbuddy-hub
把散在各个账号里的任务，收拢成一个列表

一个独立的 Windows 桌面应用：只读聚合 WorkBuddy 客户端所有账号的任务， 需要时一键切换客户端登录的账号。不修改客户端的任何数据文件，因此不随客户端版本升级而失效。

03产品形态与边界

一句话：hub 是客户端旁边的一块平级视图，不是客户端的改造版。

hub 做什么hub 不做什么
数据只读 workbuddy.db 与 jsonl 正文不改 sessions.user_id、不改客户端 db 结构
任务跨账号聚合展示、按项目/账号/状态筛选、搜索不嵌入客户端、不替换客户端任务列表
账号存档、切换、显示归属与余额不做账号分发、不做代登录
打开任务切到归属账号 → 唤起客户端 → 定位到该任务不自己渲染对话正文（v1 不做）

为什么坚持零侵入？因为 sessions.user_id 是客户端所有查询的过滤键。把它改成当前账号，任务确实「出现在原生列表里」了，但归属信息被破坏 —— 切回原账号时那些任务又不见了，而且无法还原谁是真正的属主。收益是临时的，代价是不可逆的。聚合视图能给你同样的可见性，且随时可撤销。

05三个核心机制

M1 · 跨账号任务聚合

一条 SQL 就能拿到全部任务，关键是只读打开、不阻塞客户端写入：

SELECT id, user_id, cwd, title, status, updated_at
FROM sessions
WHERE deleted_at IS NULL
ORDER BY updated_at DESC;

三个要点：

  • 用 file:...?mode=ro 打开，配合 immutable=0 让 SQLite 正确读 WAL 里尚未 checkpoint 的数据（客户端刚写完的任务不会漏）。
  • 只查索引不读正文。正文 jsonl 平均几十 KB 到几百 KB，全部读入会让首次加载变慢；改成按需读取 + 只取末尾几条做摘要。
  • 监听 workbuddy.db-wal 的修改时间，变化后做一次差量刷新，避免轮询全表。

M2 · 凭据解密与封装

这是整个方案技术含量最高的部分，但已经有可验证的参考实现（switcher 的 importCurrent()）。核心是两段：

// 1. 取主密钥：让客户端自己吐出 atRestSecretKey
WorkBuddy.exe -e "process.stdout.write(String(
  process._linkedBinding('electron_browser_workbuddy_storage').loggerGet()))"
// 环境变量 ELECTRON_RUN_AS_NODE=1，超时 30s

// 2. 解密：key = SHA256(atRestSecretKey)，AES-256-GCM
// AAD 必须按字节精确拼装，顺序错一个字节就解不开：
"WB-AAD\0" ‖ 0x01 ‖ LP("WBEV1") ‖ LP("sym-v1") ‖ suite(u32be)
          ‖ LP(keyId) ‖ 0x02 ‖ 0x00 ‖ 0x00
// LP(x) = u32be(len) ‖ bytes

加密方向写回时同理，只是把 decipher 换成 cipher，用新的随机 nonce。Rust 的 aes-gcm crate 原生支持 AAD，比 JS 里拼 Buffer 更不容易出错。

M3 · 切号引擎

切号不是改一个变量，是一次有状态的迁移，必须按顺序做完：

前置检查

目标账号凭据存在且 refreshToken 未过期；客户端当前没有 status='working' 的任务（有则弹窗确认，不静默杀进程）。

刷新令牌

refreshToken 临近过期时先换新，并把新令牌回写账号库 —— 上游会轮换 refreshToken，不回写下次就失效了。

备份

把当前 workbuddy-desktop.info 复制成带时间戳的备份，失败可一键回滚。

优雅退出

先发关闭信号，等主进程真正退出（轮询 pid），超时才强制结束。直接 kill 有 WAL 损坏风险。

写入凭据

用 atRestSecretKey 加密目标 token → 组装 envelope → 原子写入（临时文件 + rename），保留 accounts / allAccounts 结构。

重启并验证

启动客户端，等待 auth 文件被重新写入（说明登录成功），失败则自动回滚备份并报错。

这一步是整个产品风险最集中的地方。它依赖客户端的内部格式，而格式可能随版本变化。对策：把「AES 参数 + auth 文件结构」抽成一个独立的适配层 client-compat，带版本探测；一旦解密或写入校验失败，立刻停止并回滚，绝不在不确定的状态下重启客户端。

06技术选型：客户端用什么写

直接给结论：Tauri 2 + Rust（后端）+ React + TypeScript（前端）。

维度Tauri 2 / RustElectron / TS.NET 8 / WinUI
安装包体积8–12 MB90–150 MB30–60 MB
常驻内存40–60 MB180–250 MB60–90 MB
复用现有插件代码需移植 ~250 行可直接搬需移植
AES-GCM + 自定义 AADaes-gcm crate，原生 AADNode cryptoAesGcm 类
SQLite WAL 只读rusqlite bundledbetter-sqlite3Microsoft.Data.Sqlite
跨平台（mac 版）✓✓仅 Windows
UI 开发体验React 全量可用React 全量可用XAML
开发速度中快中

为什么是 Rust 而不是 Electron

  1. 它要常驻。hub 的形态是托盘应用 + 开机自启 + 后台监听 db 变化。Electron 常驻 200 MB 内存，对一个「看任务列表」的工具来说不合理；Tauri 用系统 WebView2，常驻 50 MB 左右。
  2. 核心逻辑全是系统调用，不是 DOM。取密钥要 spawn 子进程、解密要精确到字节的 AAD 拼装、读 SQLite 要处理 WAL、切号要管进程生命周期 —— 这些在 Rust 里比在 Node 里更直接，且不需要为了一个 CLI 逻辑背一个 Chromium。
  3. 解密代码越少依赖越好。这套逻辑接触的是别人的登录凭据，跑在一个只有必要依赖的二进制里，比跑在带完整 Node 生态和 npm 依赖树的运行时里更让人放心。
  4. mac 版留了门。WorkBuddy 有 macOS 客户端，凭据路径与加密方式大概率不同但结构类似。Tauri 的 #[cfg(target_os)] 分支成本远低于重做一套 Electron 打包。

代价，以及怎么控制

  • 加解密逻辑要从 TS 移植到 Rust，约 250 行。这是唯一有实际出错风险的地方。对策：先写一个对拍测试 —— 拿同一份 workbuddy-desktop.info，用已跑通的 TypeScript 实现和 Rust 实现各解一次，明文必须逐字节相同。这一步通了，后面都是常规开发。
  • Rust 开发速度慢于 TS。对策：把 UI 全部放在 React 侧，Rust 只做 5 个命令（list_tasks / list_accounts / switch_account / open_task / refresh），接口面收窄。

什么情况下应该改用 Electron：如果你希望两周内就看到能跑的原型，且不介意安装包 120 MB。前面提到的移植风险和开发速度是真实成本，Electron 在这两点上确实更省。前端代码在两种方案里完全通用，所以先做 React 界面、后端延后定型，也是一条可行路径。

07数据模型

账号库直接复用 DSH 的目录与格式，hub 和现有两个插件共享同一份账号库，互不干扰：

// ~/.dsh/workbuddy-accounts/<uid>.json   —— 格式不变，hub 只读 + 回写令牌
{ "auth": { "accessToken": "…", "refreshToken": "…",
            "expiresAt": 1794728770, "domain": "www.workbuddy.cn" },
  "account": { "uid": "697af213-…" } }

hub 自己的状态文件只存 UI 与偏好，不重复存凭据：

// ~/.workbuddy-hub/state.json
{
  "version": 1,
  "aliases": { "697af213-…": "工作号" },   // 手动备注
  "lastSwitch": { "from": "db0427fd", "to": "8bc5fd09", "at": 1792570273376 },
  "ui": { "groupBy": "account", "hideEmptyAccounts": true }
}

切号前的凭据备份放 ~/.workbuddy-hub/backups/，每次一个带时间戳的文件，保留最近 10 份，是回滚的唯一凭据。

09风险与对策

风险概率影响对策
客户端升级后 auth 格式变化中切号失效适配层隔离 + 版本探测；失败即回滚，不写坏原文件
切号时客户端正在跑任务中任务中断检测 status='working' 并强提示；不静默杀进程
token 刷新后未回写中账号下次不可用刷新即回写 + 写前比对文件未被他人改动
WAL 读取不完整低最新任务漏显示只读 URI + immutable=0；监听 wal 变化重读
明文凭据集中已接受账号库泄露即失守按你的决定不加密；文档与界面明确提示存放位置
多账号使用触及服务条款中账号被处置定位为自有账号管理工具；不做分发、不做代登录

最后一条要重申：这个工具的合理边界是管理你自己名下已登录过的账号。「帮你登录别人的账号」「对外提供账号池」都不在范围内 —— 前者技术上做不到（需要对方扫码/验证码），后者性质完全不同。
